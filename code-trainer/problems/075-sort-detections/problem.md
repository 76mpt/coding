# 075-sort-detections · 偵測框的多鍵排序

- 階段：資料結構與演算法（LeetCode 風格） / 2.6 排序與自訂比較
- 語言：Python　難度：warmup　互動方式：實作函式
- 要實作的入口：`sort_detections`
- 提示：共 4 階（`python trainer.py hint 075-sort-detections`）
- 測資：10 筆（`python trainer.py test 075-sort-detections`）

────────────────────────────────────────────────────────────────────

2.5 的前提是「資料已經排好了」。這一節講**怎麼排**，
以及一個每次都有人踩的坑：當排序的鍵不只一個、而且方向不一致的時候。

偵測器吐出一堆框，每個框是 `[cls, score, area]`：
類別編號（整數）、信心分數（浮點數）、面積（整數）。
下游要的順序是：

1. **`cls` 遞增**（同類別的框排在一起，方便逐類別做 NMS）
2. 同類別內 **`score` 遞減**（信心高的先處理）
3. `cls` 和 `score` 都相同時，**保持它們在輸入裡的原本順序**

第 3 條就是**穩定排序**。它看起來像個無關緊要的細節，其實不是：
偵測器輸出的順序通常帶著資訊（例如掃描順序、或前一幀的追蹤 ID 順序），
平手時把它打亂，下游的結果就會在每次執行之間跳動——那種 bug 非常難查。

實作 `sort_detections(dets)`，回傳兩個元素：

```
( order,        ← list[int]，排序後第 i 個框在原陣列的索引
  sorted_dets ) ← 排序後的框本身
```

`order` 存在的理由是讓「平手時的順序」變得可以檢查——
就算兩個框的三個數字完全一樣，它們的索引也不一樣。

**範例**

```python
sort_detections([[1, 0.9, 10], [0, 0.5, 20], [1, 0.95, 30]])
# -> ( [1, 2, 0],
#      [[0, 0.5, 20], [1, 0.95, 30], [1, 0.9, 10]] )

sort_detections([[2, 0.8, 1], [1, 0.8, 2], [1, 0.8, 3], [2, 0.8, 4], [1, 0.9, 5]])
# -> ( [4, 1, 2, 0, 3],
#      ... )
# cls=1 的三個：score 0.9 先（索引 4），然後 0.8 平手 → 索引 1 在 2 前面
# cls=2 的兩個：0.8 平手 → 索引 0 在 3 前面

sort_detections([])
# -> ([], [])
```

## `reverse=True` 不等於把結果倒過來

兩個鍵的方向相反，所以你**不能**寫 `sorted(dets, key=..., reverse=True)`——
那會把 `cls` 也變成遞減。

那「先按 score 排好再倒過來」呢？這裡有個 Python 的細節值得知道：

- `sorted(x, key=f, reverse=True)` **保持**相等元素的原順序（穩定）
- `list(reversed(sorted(x, key=f)))` 會把相等元素的順序**倒過來**

兩者對「不平手」的資料結果一樣，一旦有平手就不一樣。這題的測資裡平手很多，
所以第二種寫法會直接錯。

至於正確的做法，有兩條路，兩條都值得你自己想出來——
一條是想辦法讓「一個鍵」同時表達兩個方向，
另一條是利用穩定性，分兩次排。

**限制**
- `0 <= n <= 2 * 10^5`
- `cls` 是整數（可能是 0 或負數），`score` 是浮點數（可能是負數或 0），`area` 是整數
- `order` 必須是 `0 .. n-1` 的一個排列
- `sorted_dets[i]` 必須就是 `dets[order[i]]`
- 大測資有 20 萬個框，裡面**大量平手**，並有時間上限

前兩題都靠排序。這題問一個更基本的問題：**什麼時候排序是浪費的？**

偵測器一幀可以吐出上百萬個候選框，每個框帶一個信心分數。
分數是**量化過的整數，範圍 0 到 1000**——
深度學習的推論 pipeline 常這樣存，省記憶體也省頻寬。

NMS 之前要先砍掉大部分候選，只留分數最高的 `k` 個。
但「留 k 個」在有平手的時候並不精確：如果第 k 名那個分數有五十個框都是，你要留哪些？
實務上的做法是**定一個門檻，然後回報這個門檻會留下多少東西**，讓下游決定要不要調。

實作 `top_k_scores(scores, k)`，回傳三個元素：

```
( kth,            ← 第 k 大的分數（含重複，也就是遞減排序後的第 k 個；k 從 1 算起）
  count_at_kth,   ← 等於 kth 的分數有幾個
  n_above )       ← 嚴格大於 kth 的分數有幾個
```

這三個數之間有一個關係一定成立，可以拿來自我檢查：

```
n_above < k <= n_above + count_at_kth
```

**範例**

```python
top_k_scores([3, 1, 4, 1, 5, 9, 2, 6], 1)   -> (9, 1, 0)
top_k_scores([3, 1, 4, 1, 5, 9, 2, 6], 3)   -> (5, 1, 2)
top_k_scores([3, 1, 4, 1, 5, 9, 2, 6], 8)   -> (1, 2, 6)
top_k_scores([2, 2, 2, 2, 5, 5, 1], 4)      -> (2, 4, 2)
```

第三個例子：遞減排序是 `[9,6,5,4,3,2,1,1]`，第 8 個是 1，
而 1 出現兩次、有 6 個比它大。
注意 `k = 7` 和 `k = 8` 會得到**完全一樣**的三個數——它們落在同一個平手群裡。

## 值的範圍比 n 小的時候，排序不是下限

排序的 `Ω(n log n)` 下限有一個前提：**你只能比較兩個元素的大小**。

這題不在那個前提裡。分數是 0 到 1000 的整數，所以你可以**直接拿它當索引**——
不用比較，只要數數。想清楚這件事，整題就只剩幾行。

`n = 10⁶` 時，`O(n log n)` 是兩千萬次比較；`O(n + M)`（`M = 1001`）只要一百萬次加法。

所以這題**禁用任何排序**。不是為了刁難——
是因為一旦用了排序，你就看不到「值域有界」這個條件值多少錢。
這個取捨在 077 也出現過（座標範圍小的時候用差分陣列不必排序），
而它在 2.9 會再變一次形。

**限制**
- `1 <= n <= 10^6`
- `0 <= scores[i] <= 1000`，整數
- `1 <= k <= n`
- **禁用 `sorted`、`.sort()`、`heapq`**。`collections.Counter` 可以用來計數，
  但不要用它的 `most_common()`——那也是排序
- 大測資 `n = 10^6` 並有時間上限

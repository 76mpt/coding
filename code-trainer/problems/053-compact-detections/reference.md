# 053-compact-detections · 就地過濾偵測框 — 參考解

## 標準解

```python
def compact(scores, threshold):
    write = 0
    for x in scores:              # x 就是「讀指標」指到的東西
        if x >= threshold:
            scores[write] = x     # 覆寫到寫指標的位置
            write += 1
    return write, scores[:write]
```

時間 O(n)，額外空間 O(1)（回傳的切片不算，那是題目要的輸出）。

這已經是最佳解——你至少要看過每個元素一次才能決定它去留，所以 O(n) 是下界。

## 為什麼覆寫是安全的

這是這題唯一需要證明的事：**寫指標永遠 <= 讀指標**。

讀指標每一步都前進 1；寫指標只有在「要保留」時才前進 1。所以寫指標的步數
最多等於讀指標的步數，`write <= read` 恆成立。

這代表 `scores[write]` 這個格子要嘛裝著**已經讀過的舊資料**（可以丟），
要嘛就是 `scores[read]` **自己**（自己覆寫自己，無害）。
無論哪種，你都不會蓋掉還沒讀到的東西。

這個「兩個指標同速度不同」的模式叫**快慢指標**，是雙指標的第二種形態
（006 用的是**對撞指標**，兩個指標從兩端往中間走）。它還會出現在：

- 移除指定元素、去重（LeetCode 26/27/283）
- 判斷連結串列有沒有環（Floyd 判圈法，快指標一次走兩步）
- 找連結串列的中點（快指標到底時慢指標剛好在中間）

## 另一種寫法

```python
def compact(scores, threshold):
    kept = [x for x in scores if x >= threshold]
    return len(kept), kept
```

**一樣是 O(n) 時間，測資分不出來，而且更 pythonic。**
實務上寫這個沒問題，程式碼短又清楚。

差別在額外空間：這版是 O(n)，就地版是 O(1)。什麼時候這個差別是真的？

- 陣列很大而記憶體吃緊（嵌入式裝置、GPU 上的中間結果）
- 這個 list 還被別的地方持有參考，你希望對方也看到過濾後的結果
- 面試官明確要求 in-place

什麼時候不重要？多數應用程式的日常程式碼。
**知道兩種寫法、也知道差別在哪，比堅持用哪一種重要。**

## 常見錯誤

1. **用 `>` 而不是 `>=`**——題目說門檻本身要保留。
   `compact([5,5,5], 5)` 會回 `(0, [])` 而不是 `(3, [5,5,5])`。

2. **在迴圈裡刪除元素**——`for i in range(len(scores)): if ...: scores.pop(i)`。
   邊走邊刪會跳過元素（刪掉 i 之後原本的 i+1 變成了 i，但迴圈下一步跳到 i+1），
   而且 `pop(i)` 本身是 O(n)，整體變成 O(n²)。
   `[1, 9, 1, 9, 1, 9]` 這種交錯的測資會抓到。

3. **`scores[:write]` 切太早**——寫在迴圈裡面，拿到的是還沒填完的前綴。

4. **另外開一個 `write_list` 然後 append**——那就是新 list 版本，
   邏輯正確、測資會過，但沒練到這題要練的東西。做完至少自己改一次就地版。

5. **回傳 `scores` 整個而不是 `scores[:write]`**——後面還留著沒被覆蓋的舊資料。
   `compact([9,2,7,1,8,3], 5)` 的 `scores` 掃完是 `[9,7,8,1,8,3]`，
   後面那個 `1,8,3` 是殘留，不是答案的一部分。

## 延伸

真實的偵測後處理在這一步之後是 **NMS（non-maximum suppression）**：
分數過濾只丟掉「不夠有信心」的框，NMS 再丟掉「跟更好的框重疊太多」的框。
你會在 S5 的 CV 實作節點寫到它，而 NMS 的內層迴圈就是在算 IoU——
那正是 010-iou-matrix 那題。

下一題會練雙指標的第三種形態：**滑動視窗**，兩個指標都往同一個方向走，
但中間夾著的區間會伸縮。

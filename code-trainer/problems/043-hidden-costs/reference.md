# 043-hidden-costs · 字串串接與 list 操作的隱藏成本 — 參考解

## 標準解

```python
def build_report(records):
    lines = [f"{label}:{score:.3f}" for label, score in reversed(records)]
    return "\n".join(lines)
```

兩行，**O(n)**。空 list 時 `join([])` 回傳 `""`，不用特判。

## 陷阱一：字串累加是 O(n²)

```python
s = ""
for line in lines:
    s += line + "\n"
```

**Python 的字串是不可變的**——`s += x` 沒辦法「就地加長」，它必須：

1. 配置一塊 `len(s) + len(x)` 的新記憶體
2. 把舊的 `s` 整個複製過去
3. 接上 `x`
4. 讓舊的 `s` 被回收

第 k 圈複製 k 個字元，總共 `1+2+…+n = n(n+1)/2 = O(n²)`。

`join` 的做法完全不同：**先走一遍算出總長度，配置一次，再填進去**。O(n)。

> **CPython 有個特例優化**：當 `s` 的 refcount 是 1（沒有別人指向它）時，
> `s += x` 會嘗試就地 realloc。所以你在小規模測試時可能感覺不到差別。
> **但那是實作細節**——把 `s` 存進 list、傳給函式、或換成 PyPy，優化就失效，
> 效能斷崖式下降而且毫無徵兆。**不要依賴它。**

## 陷阱二：`list.insert(0, x)` 是 O(n)

list 在記憶體裡是**一塊連續的陣列**（存的是指標）：

```
索引     0    1    2    3
       [ a ][ b ][ c ][ d ]

insert(0, x) → 後面四個全部往右搬一格，才能空出位置
```

| 操作 | 複雜度 |
|---|---|
| `append(x)` | **O(1)** 攤銷 |
| `pop()`（尾端） | **O(1)** |
| `insert(0, x)` | **O(n)** |
| `pop(0)` | **O(n)** |
| `x in lst` | O(n) |
| `lst[i]` | O(1) |

**尾端便宜、頭端昂貴**——這是陣列的本質，不是 Python 的缺陷。

需要兩端都快的話用 `collections.deque`（雙向佇列，`appendleft`/`popleft` 都是 O(1)）。
那是 **2.3 節堆疊與佇列**的主角，BFS 一定會用到。

## 「反序」的三種寫法

```python
reversed(records)      # 迭代器，不複製 → O(1) 空間
records[::-1]          # 新 list，複製一份 → O(n) 空間
records.reverse()      # 就地反轉 → O(1) 空間，但改動了呼叫者的 list ⚠️
```

**`reversed()` 最好**：不複製、不改動輸入。

`records.reverse()` 會**修改呼叫者傳進來的 list**——這是副作用，
呼叫端會發現自己的資料被動了手腳。你在 017-merge-inventory 遇過同一條規格（「不可以修改傳入的 a 和 b」）。

## 為什麼這節叫「複雜度直覺」

因為這兩個陷阱**在小資料上完全看不出來**：

| n | 字串 += | join |
|---|---|---|
| 100 | 0.00002 秒 | 0.00001 秒 |
| 10,000 | 0.02 秒 | 0.001 秒 |
| 100,000 | **2+ 秒** | 0.01 秒 |

**你在開發時用 100 筆測試，一切正常；上線後資料變成 10 萬筆，程式就掛了。**

所以「複雜度直覺」不是背 Big-O 定義，是**看到一段程式碼就知道它在大資料下會不會爆**。
養成的方法只有一個：**知道每個常用操作的成本**。

### 值得背下來的表

| 操作 | 成本 | 陷阱 |
|---|---|---|
| `s += x`（迴圈裡） | O(n²) | 用 `"".join()` |
| `lst.insert(0, x)` / `lst.pop(0)` | O(n) | 用 `deque` 或反轉 |
| `x in list` | O(n) | 用 `set` |
| `lst = lst + [x]` | O(n) | 用 `append` |
| `sorted()` | O(n log n) | — |
| `dict[k]` / `set` 的 `in` | O(1) | 要可 hash |
| 巢狀迴圈 | O(n·m) | 想想能不能用索引取代內層 |

## 常見錯誤

1. **迴圈裡 `s += line + "\n"`** —— 大測資超時，而且結尾會多一個換行。
2. **`insert(0, ...)`** —— 同樣超時。
3. **結尾多一個換行** —— `"\n".join()` 天生不會有；用 `+=` 的話要記得最後切掉。隱藏測資檢查 `not got.endswith("\n")`。
4. **格式寫成 `:.3` 而不是 `:.3f`** —— `:.3` 是「三位有效數字」（`0.9` 會變 `0.9`），`:.3f` 才是「三位小數」（`0.900`）。
5. **用 `records.reverse()`** —— 會改動呼叫者的 list。能過測資，但是副作用。
6. **忘記反序** —— 題目要由後往前。

## 延伸

這題的兩個陷阱在 C++ 裡有直接對應（`std::string` 的 `+=`、`vector::insert(begin())`），
**3.1「卡時限與 I/O 優化」**整節就在講這類常數優化——那時候 1 秒的時限會讓你真正感受到差別。

而「先收集再一次組合」這個模式，在資料管線裡到處都是：
累積 batch 再一次寫檔、累積梯度再一次 step、累積 log 再一次 flush。
**每一次「真的動手」都有固定成本，所以要少做幾次、每次做多一點。**

072 你寫的二分搜尋有一個前提：陣列整體單調。這題把那個前提打破。

一個嚴格遞增的陣列（元素互不相同）被**旋轉**過——從某個位置切開，前後兩段交換：

```
[0, 1, 2, 4, 5, 6, 7]   旋轉之後   [4, 5, 6, 7, 0, 1, 2]
```

整體不再遞增，但它仍然是「兩段各自遞增」的。

這在實務上很常見：**環形緩衝區**（ring buffer）就長這樣。
追蹤器用一個固定大小的陣列存最近 n 幀的時間戳，寫滿了就從頭蓋掉，
所以你拿到的陣列永遠是被旋轉過的，而旋轉量就是「最舊那一筆在哪裡」。

實作 `search_rotated(nums, targets)`，回傳兩個元素：

```
( pivot,   ← 最小元素的索引（旋轉點，也就是最舊那一筆的位置）
            沒有旋轉時是 0；空陣列時是 -1
  found )  ← list，每個 target 在 nums 裡的索引；不存在就是 -1
```

**範例**

```python
search_rotated([4, 5, 6, 7, 0, 1, 2], [0, 3, 4, 2, 7])
# -> (4, [4, -1, 0, 6, 3])

search_rotated([1, 2, 3, 4, 5], [1, 5, 6])
# -> (0, [0, 4, -1])            完全沒旋轉，pivot 就是 0

search_rotated([2, 1], [1, 2, 3])
# -> (1, [1, 0, -1])

search_rotated([], [1])
# -> (-1, [-1])
```

## 旋轉之後還剩下什麼

二分搜尋真正需要的不是「陣列遞增」，
而是「**我能從一次比較判斷出答案在哪一邊**」。

旋轉之後整體不遞增了，但你每次看到 `nums[mid]`，仍然判斷得出一些事情。
想清楚這件事：`nums[mid]` 跟**兩端的元素**比起來的大小關係，各自告訴你什麼？
找 `pivot` 和找 `target` 都靠這一點。

另外一個提醒，值得先花兩分鐘想：
`pivot` 找到之後，有一個很簡單的**索引轉換**能讓你把 072 寫好的 `lower_bound`
原封不動拿過來用，一個 `if` 分支都不用加。
找那個轉換，比手寫一堆「哪一半是有序的」的條件分支可靠得多——
後者是這題最常見的 bug 來源。

**限制**
- `0 <= n <= 2 * 10^5`，`0 <= len(targets) <= 2 * 10^4`
- `nums` 是某個嚴格遞增陣列的旋轉結果，**元素互不相同**
- 旋轉量可以是 0（完全沒旋轉）
- 找 `pivot` 和每個查詢都必須是 **O(log n)**
- 大測資有 20 萬個元素、2 萬個查詢並有時間上限。線性掃描會超時

# 073-search-rotated · 旋轉過的陣列裡搜尋 — 參考解

## 標準解

```python
def search_rotated(nums, targets):
    n = len(nums)
    if n == 0:
        return (-1, [-1] * len(targets))

    # 1) 二分找旋轉點：最小元素的索引
    lo, hi = 0, n - 1
    while lo < hi:
        mid = (lo + hi) // 2
        if nums[mid] > nums[hi]:       # mid 落在「較大」那一段 → 斷點在右邊
            lo = mid + 1
        else:                          # mid..hi 連續遞增 → 斷點在左邊或就是 mid
            hi = mid
    pivot = lo

    # 2) 虛擬索引：nums[(pivot + i) % n] 對 i = 0..n-1 是遞增的
    def find(t):
        a, b = 0, n                    # 跟 072 的 lower_bound 完全一樣
        while a < b:
            mid = (a + b) // 2
            if nums[(pivot + mid) % n] < t:
                a = mid + 1
            else:
                b = mid
        if a < n and nums[(pivot + a) % n] == t:
            return (pivot + a) % n
        return -1

    return (pivot, [find(t) for t in targets])
```

## 為什麼跟 `nums[hi]` 比，而不是 `nums[lo]`

這是這題最值得記住的一個細節。

跟 `nums[hi]` 比：
- `nums[mid] > nums[hi]` → `mid` 到 `hi` 之間必有下降 → 最小值在 `(mid, hi]`
- `nums[mid] < nums[hi]` → `mid` 到 `hi` 單調遞增 → 最小值在 `[lo, mid]`

兩種情況都乾淨。而跟 `nums[lo]` 比就不行：
**完全沒旋轉**的陣列 `[1,2,3,4,5]`，`nums[mid] = 3 > nums[lo] = 1`，
照「大於左端就往右找」的邏輯你會往右跑，但正確答案是 0——徹底錯。

你得額外加一條「先判斷整體有沒有旋轉」的分支才能補救。
跟右端比不需要那條分支，因為「沒旋轉」在右端的比較裡自然就是
「`nums[mid] < nums[hi]` 恆成立」，而那正好把 `hi` 一路推到 0。

**通則**：二分的比較基準要選那個「邊界情況也落在正確分支」的一端。
選錯不是寫不出來，是得多寫一堆特例——而特例就是 bug 的住處。

## 為什麼虛擬索引是對的

設旋轉前的陣列是 `s`（嚴格遞增），旋轉 `k` 格之後 `nums[j] = s[(j + k) % n]`。
最小元素 `s[0]` 落在 `nums` 的哪裡？滿足 `(j + k) % n == 0` 的 `j`，
也就是 `j = (n - k) % n` —— 這正是 `pivot`。

於是 `nums[(pivot + i) % n] = s[(pivot + i + k) % n] = s[i]`（因為 `(pivot + k) % n == 0`）。

所以虛擬索引 `i` 取到的就是 `s[i]`，而 `s` 是遞增的。
**旋轉只是在索引上套了一個模 n 的位移，順序關係完全沒有被破壞。**

這個想法比它在這題的用途更廣：任何「環形」的資料結構
（ring buffer、循環佇列、環形鏈結串列）都可以用一個偏移量 + 取模，
把它變回線性的來處理。

## 另一種做法：直接在旋轉陣列上二分

不先找 `pivot`，每輪判斷「哪一半是有序的」：

```python
def find_direct(nums, t):
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == t:
            return mid
        if nums[lo] <= nums[mid]:               # 左半段 [lo, mid] 有序
            if nums[lo] <= t < nums[mid]:
                hi = mid - 1
            else:
                lo = mid + 1
        else:                                   # 右半段 [mid, hi] 有序
            if nums[mid] < t <= nums[hi]:
                lo = mid + 1
            else:
                hi = mid - 1
    return -1
```

這是 LeetCode 33 的標準答案，一次二分就解決，**不需要先找 pivot**，常數更小。

但它有四條分支、六個比較，而且每個 `<` 和 `<=` 都不能錯一個。
我建議你先寫得出「找 pivot + 虛擬索引」那版——
它把一個難問題拆成兩個你已經會的問題，而且第二步是現成的。
等那版寫熟了，再把這版寫一次當作練習，你會更清楚那六個比較為什麼各自要那樣寫。

（這題要求回傳 `pivot`，所以你無論如何都得找它。）

## 複雜度

- 找 `pivot`：**O(log n)**
- 每個查詢：**O(log n)**
- 總計 **O(log n + q·log n)**，空間 **O(q)**（只有輸出）

大測資 `n = 2×10⁵`、`q = 2×10⁴`：約 `2×10⁴ × 18 = 36` 萬次迴圈。
線性掃描是 `4×10⁹`。

## 常見錯誤

1. **跟 `nums[lo]` 比** — 上面講過，`[1,2,3,4,5]`（沒旋轉）那筆會抓到。
2. **`pivot` 的二分用了 `[0, n]`** — `hi = n` 會讓你讀到 `nums[n]`，`IndexError`。
   這裡的答案一定是真實索引，所以上界是 `n - 1`。
3. **`lower_bound` 找到位置就直接回傳** — 忘了驗證 `nums[那個位置] == t`。
   查詢不存在的值（例如第一筆的 `3`）會回傳一個錯的索引而不是 `-1`。
4. **忘了 `a == n` 的情況** — `t` 比所有元素都大時 `a = n`，
   `nums[(pivot + n) % n] = nums[pivot]` 不會爆錯，但那是最小元素，比較結果是「不等於」，
   所以剛好回 `-1`——**碰巧對**。別依賴它，明確寫 `a < n`。
5. **`% n` 漏掉或放錯位置** — 寫成 `nums[pivot + mid]` 會 `IndexError`；
   寫成 `(pivot + mid % n)` 則是運算子優先序的錯（`%` 比 `+` 緊），結果完全不對。
6. **空陣列沒特判** — `nums[hi]` 在 `hi = -1` 時不會爆（Python 的負索引），
   但會讀到錯的東西。`n == 0` 要在最前面擋掉。

## 延伸

- **有重複值的版本**（LeetCode 81 / 154）：`nums[mid] == nums[hi]` 時你**無法判斷**
  斷點在哪一邊（想想 `[1,1,1,0,1]`），只能把 `hi` 減 1 慢慢退，
  最壞情況退化成 **O(n)**。而且可以證明這是無法避免的——
  有重複值時任何演算法最壞都要看 O(n) 個元素。
  這題保證元素互不相同，就是為了讓 `O(log n)` 成立。
- **浮點二分**：2.5 的最後一題，區間是連續的，終止條件要換掉。
- **007-min-shipping-capacity**：二分答案。這題和 072 都是在「真實存在的陣列」上二分，
  007 的陣列是虛構的。三題做完，2.5 就收齊了。

**跟你的方向的關係**：環形緩衝區是即時系統的標配。
相機和 IMU 的驅動幾乎都是把最近 N 筆資料寫進一個固定大小的環形陣列，
所以你拿到的時間戳序列永遠是旋轉過的。
要「找出時間 t 附近的那幾幀」，就是這題——先找出寫入指標在哪（`pivot`），
再在虛擬索引上二分。055 你用雙指標處理時間對齊，
那是因為兩邊都有序且同向前進；查詢是隨機順序、而資料存在環形緩衝區裡時，
就只能用這題的做法。
